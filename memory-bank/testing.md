# Сборка, аппаратные проверки и права

## Без аппаратных записей

Из корня qc71_laptop:

```sh
make -j4 W=1
python3 tests/test_fan.py
python3 tests/test_ec_and_led.py
python3 tests/test_hardware_helper.py
python3 tests/test_power_observer.py
python3 -m py_compile tools/hardware_test.py tools/observe_power.py
python3 tools/hardware_test.py snapshot
```

Mock-проверки не доказывают совместимость адресов EC. `snapshot` только читает известные sysfs/debugfs файлы, не сканирует весь EC. Результаты физических опытов записаны в [progress.md](progress.md).

## Временная загрузка новой сборки

Не устанавливать через DKMS и не автозагружать до физических проверок. Убедиться, что tuxedo_keyboard/uniwill_wmi/tuxedo_io/uniwill_laptop и их EC контроллеры не работают параллельно. Новая сборка не загружается автоматически после make.

Команды выполняет пользователь из своего терминала:

```sh
cd /home/paveliarch/projects/laptop/qc71_laptop
sudo modprobe led_class_multicolor
sudo rmmod qc71_laptop
sudo insmod ./qc71_laptop.ko debugregs=1 keyboard_backlight=1 fan_control=1
cat /sys/module/qc71_laptop/parameters/keyboard_backlight_protocol
sudo python3 tools/hardware_test.py snapshot
journalctl -k -b --no-pager -g qc71_laptop -n 45
```

Маркер должен быть `intel-ac-dc-v1`; новая Intel сборка имеет srcversion `A47EBF4D6DB5B96BF602F3B` и уже загружена на2026-11-01. Изменения Python helper не требуют перезагрузки модуля. Ранее загруженная D58D518BCA80569B33246D1 использует старую яркость078c и не подходит для `keyboard-led`.

Опции LED/PWM экспериментальны и только открывают интерфейсы; не включают manual_control и не задают цвет/обороты на probe. Если insmod неудачен, исходный установленный модуль можно вернуть: `sudo modprobe qc71_laptop`. Не заменять установленный .ko этой сборкой до проверки. `debugregs=1` также открывает root-only **записываемые** регистры: не писать неизвестные адреса и не выдавать к ним общий доступ.

В snapshot нужны support_1/2, CTRL1/2, fan control, Intel AC/DC controls; в журнале — успешность каждого submodule. Отказ lightbar=-ENODEV ожидаем при support_1=0. Маркер backend без зарегистрированной LED не означает успешную инициализацию.

## Новый Intel LED через стандартный интерфейс

```sh
sudo python3 tools/hardware_test.py keyboard-led
```

Только новая сборка, AC0 online1 и manual_control=0. Исходный настроенный профиль должен быть включён, без rainbow/default/black, а RGB кэша должен совпадать с raw AC RGB; иначе опыт откажет до записей. Оставить адаптер подключённым. По приглашению нажать обычную клавишу встроенной клавиатуры, чтобы разбудить подсветку; назвать исходную яркость. Helper меняет только стандартные LED файлы, raw EC читает для диагностики.

Последовательность ожиданий:

1. **Красный**, brightness255, 6 секунд: максимальный настроенный уровень.
2. **Красный**, brightness64, 6 секунд: заметно тусклее предыдущего.
3. brightness0, 4 секунды: подсветка **выключена**.
4. Возврат исходного RGB и настроенной яркости, проверка readback.

Helper ждёт стабилизации асинхронного LED callback до2с на этап. Числовой успех нужно сопоставить с физическим наблюдением: красный ли цвет, стало ли тусклее, погас ли свет, что произошло после восстановления. Getter показывает настроенный профиль, не скрытый native Fn/idle уровень; точный возврат исходной физической Fn-яркости не обещается. Его при необходимости вернуть Fn+F7.

2026-11-01 пользователь подтвердил все четыре стадии AC опыта, включая восстановление белого. ACcontrol04→01→11→02, выходыRGBc8/0/0→32/0/0→0/0/0→64/64/64. Отчёт и ограничения getter — в hardware.md.

При смене источника питания тест прерывается. Пока AC отключён, helper не должен записывать исходные AC цвета через активный DC интерфейс; восстановление AC остаётся отложенным до возвращения адаптера. В штатном опыте питание не менять. DC профиль проверять отдельно после успешного AC опыта.

Сохраняется rainbow при изменении одной яркости; изменённый RGB выбирает static. Отдельного интерфейса эффектов пока нет. Источник протокола и границы подтверждения — в [architecture.md](architecture.md).

## Переключение AC/DC и DC LED

Перезагрузка модуля для этих Python helpers не нужна. Начать с подключённым адаптером:

```sh
sudo python3 tools/observe_power.py
```

Это только чтение. По приглашениям разбудить встроенную клавиатуру обычной клавишей, затем физически отключить и подключить адаптер. Fn не нажимать. При текущих сохранённых профилях ожидается **белый на AC → красный на DC → белый на AC**, если свет активен. Скрипт печатает ожидаемый цвет из сохранённого профиля и спрашивает фактические цвет/яркость на каждой стадии.

Для DC недостаточно AC0/online=0: драйвер учитывает все системные источники питания. Helpers также исключают другие online non-battery supplies; источники со scope=Device не относятся к питанию системы. При неизвестном состоянии опыт отказывает до записи. На текущем устройстве оба USB-C supply имеют scope=System и online0.

До чтения `brightness` скрипт ждёт два стабильных снимка `multi_intensity` нового профиля. Getter яркости сам может запросить refresh и тем самым скрыть отказ notifier. Проверяется сохранность обоих raw профилей с исключением самосбрасывающегося APPLY. При одинаковых цветах результат INCONCLUSIVE; программа не создаёт искусственных различий. Другие GUI/readers могут вызывать getter параллельно, поэтому вывод ограничен наблюдаемым обновлением кэша до getter именно этого скрипта.

После observer адаптер снова подключён. Затем отдельно отключить адаптер, оставить питание от батареи и выполнить:

```sh
sudo python3 tools/hardware_test.py keyboard-led --power-source dc
```

Ожидается **яркий СИНИЙ6с → тусклее СИНИЙ6с → OFF4с → исходный DC цвет/уровень** (сейчас красный, configured level2). Проверяются активные DC07eb/07ec..ee, сохранность AC07ea/0769..6b и manual/fan/CTRL2. Адаптер во время опыта не подключать. При смене источника восстановление своего профиля остаётся отложенным, а его цвета не записываются в противоположный банк.

2026-11-01 оба опыта прошли. Пользователь подтвердил белый→красный→белый при AC/DC/AC, а также DC синий→тусклее→OFF→красныйrestore. Кэш успевал обновиться до brightness_get скрипта, raw профили при переключении не менялись; в DC LED тесте AC банк сохранился. Подробнее — hardware.md. Повторять без нового основания не нужно.

## Батарея и вентиляторы — отдельные опыты

```sh
sudo python3 tools/hardware_test.py battery --threshold 90
sudo python3 tools/hardware_test.py fans
```

Батарея: временный лимит90 вместо исходного80, readback через3с, затем восстановление80. Этот опыт уже прошёл: read90, BAT0 80%, Charging; после восстановления80 вернулся Not charging. Позже естественная зарядка78→80 также завершилась Not charging на лимите80. Остановка на иных выбранных порогах не проверялась.

Fans: только из manual_control=0 / mode2 и при CPU/GPU<75°C. Оба вентилятора 8с на100% — **ожидается ускорение**; затем8с на~90% — **небольшое замедление относительно100%**; затем возврат BIOS и наблюдение — **при простое ожидается замедление**, с учётом температуры. Helper выводит RPM/температуры по фазам и просит подтвердить поведение обоих вентиляторов. Если уже был ручной режим, тест откажет, чтобы не нарушить чужую политику. Произвольные низкие PWM не тестируются.

2026-11-01 опыт прошёл:3611/3483→5629/5220→5284/4945→3611/3483RPM, пользователь подтвердил все стадии. На выходеmanual0/mode2/CTRL1=00/FAN_CTRL=00. Повторять короткий опыт без нового основания не нужно.

`pwm1_enable` общий для обоих каналов. После BIOS handoff raw PWM может сохранять последнее число — это не ошибка, если boost снят и manual_control=0. Число PWM не доказывает текущую физическую скорость.

Скрипт выполняет восстановление в finally при обычной ошибке, Ctrl-C, SIGTERM/SIGHUP. SIGKILL/сбой ядра не позволяют выполнить finally. Явный возврат вентиляторов:

```sh
sudo python3 tools/hardware_test.py bios
```

Это пишет manual_control=0: драйвер снимает boost под fan mutex, затем отдаёт управление BIOS; helper проверяет readback. Смена AC/DC уже проверена. Остаются suspend/resume и длительное наблюдение ручного PWM. Ожидания и физический результат записывать в progress.md.

## Следующий PM опыт после AC/DC

Сначала проверять сон из BIOS режима, сохраняя подключённый адаптер и исходный белый цвет. Текущий доступный sleep: `[s2idle] deep`; переключать его для первого опыта не нужно. Read-only baseline уже подтвердил manual0/mode2, поэтому повторная запись `bios` не требуется.

```sh
sudo python3 tools/hardware_test.py snapshot | tee /tmp/qc71-pm-before.json
cat /sys/power/mem_sleep
systemctl suspend
```

Следующий блок выполнить отдельно, **только после физического пробуждения и возвращения в сеанс**. Возврат systemctl сам по себе не доказывает завершённый sleep/resume.

```sh
sudo python3 tools/hardware_test.py snapshot | tee /tmp/qc71-pm-after.json
journalctl -k -b --no-pager -g 'qc71_laptop|PM: suspend' -n 80
```

После wake ожидаются manual0/mode2/boost0, сохранённые профили и лимит80. В журнале нужна новая пара suspend entry(s2idle)/exit. Спросить, сохранился ли **белый** цвет и какая яркость сразу после wake и после обычной клавиши встроенной клавиатуры (не Fn). При простое ожидается обычная автоматическая работа обоих вентиляторов; краткий разгон при resume зависит от температур. Изменение idle timer и выходных RGB после клавиши допустимо.

PM1 прошёл19:11:22→19:11:29 МСК: настройки сохранились, пользователь подтвердил активный белый после пробуждения клавишей и обычную работу обоих вентиляторов. Из46полей снимка изменились только6телеметрических. Наблюдения до wake-клавиши и отдельной оценки физической яркости не было. Scope: один s2idle на AC, direct PWM до сна не работал; deep этим не проверялся.

## PM2: снятие принадлежащего драйверу direct PWM

```sh
sudo python3 tools/hardware_test.py fans-suspend
```

Обязателен интерактивный запуск на AC из BIOS/manual0/mode2, с debugregs=1 и температурами ниже75°C. Helper задаёт обоим вентиляторам около90% на8с: **ожидается ускорение обоих**. Затем на приглашении оставить этот терминал открытым, усыпить ноутбук через меню рабочего стола либо `systemctl suspend` в **другом** терминале. Пробудить ноутбук и только после этого нажать Enter в helper. Он сам не вызывает suspend и не принимает --no-prompt.

Перед восстановлением helper читает состояние: ожидаются mode2/boost0 без replayPWM, manual1 остаётся по логике драйвера; если firmware само сбросилоmanual0, полный BIOS также безопасен. CTRL1 и manual sysfs должны совпадать. При простое после wake **ожидается замедление обоих относительно90%**, скорость зависит от температуры. Пользователь подтверждает ускорение и замедление. Отсутствие сна обычно оставитmode1/boost40 и даст ошибку; один readback не доказывает физический сон, поэтому нужен журнал:

```sh
journalctl -k -b --no-pager -g 'qc71_laptop|PM: suspend' -n 80
```

В finally helper явно возвращает BIOS/manual0 и печатает итог даже при обычной ошибке, Ctrl-C или EOF. SIGKILL/сбой ядра исключает такой finally, как и у других bounded тестов; отдельный `bios` остаётся доступен. Ручной PWM автоматически не воспроизводится после resume.

PM2 прошёл19:33:35→19:33:40 МСК. До сна5310/4945RPM, mode1/manual1/boost40; после wake ДО cleanup2542/2495RPM, mode2/manual1/boost0. Пользователь подтвердил ожидаемое поведение обоих. Затем finally вернул manual0/mode2/boost0. Это проверило именно owned PM release без replay, в отличие от PM1. Повторять без нового основания не нужно. [Подготовленный пакет](install.md) уже установлен и проверен; остаются постоянные options и обычный modprobe.

Для регулярной работы debugregs не сохраняется. При следующем debugregs=N весь каталог qc71 debugfs отсутствует, что ожидаемо; полный snapshot печатает ENOENT для его полей, а init журнал — debugfs=-19. Аппаратные tests, требующие raw registers, после этого откажут до записи. Короткие уже пройденные эксперименты повторно включать не требуется.

Пакет и постоянные options уже установлены. Обычный modprobe без явных параметров прошёл20:00:47: keyboard/fanY, debugN, A47, BIOSmanual0/mode2, LEDwhite/128 и threshold80 проверены чтением; пользователь подтвердил белый свет и обычные оба вентилятора. Полный boot после установки отдельно не тестировался. Текущий результат и rollback — в install.md; новые повторные аппаратные tests без изменений или неисправности не нужны.

## Диагностические команды первой сессии

`keyboard-observe` только читает настройки до/после одного Fn+F7 на встроенной клавиатуре. При исходном белом RGB ожидается белый цвет, если свет включится. Native Fn сам меняет состояние BIOS, helper его не отменяет.

`keyboard-intel-brightness` — изолированная проба ACcontrol07ea: исходный белыйRGB, control02, AC0 online1, manual0. Команда0c на8с ожидает **более яркий белый**. Этот эффект подтверждён. Восстановление теперь посылает исходныйlevel2 с APPLY —0a, а проверяет стабильный02. Ранняя версия посылала raw02 и не возвращала выходную яркость, поэтому не использовать её как пример правильного восстановления.

`keyboard --color red` — прежний диагностический опыт с rawRGB/CTRL2 backup для старого backend. На новом backend он отказывает с указанием `keyboard-led`: актуальный тест не восстанавливает устаревшие CTRL2/trigger.

Immediate1801/1802/1803/1805/1808 читаются по одному известному адресу через debugfs/ec (небуферизованный read1), без записей в эти адреса. На P527 immediate1802 остаётся0 даже при горящем белом, не считать его яркостью.

## Права для работы агента

В текущей Codex среде UID1000 и `no new privileges`: обычный sudo не работает. Изменение sudoers само по себе это ограничение не снимает. Пока проще выполнять команды в своём терминале и передавать вывод/наблюдения.

Для самостоятельных опытов нужна среда исполнения с доступом к хосту без этого ограничения и ограниченный root helper. При таком варианте скопировать проверенный `tools/hardware_test.py` в root-owned `/usr/local/libexec/qc71-hardware-test`, с root-owned родительскими каталогами, фиксированным интерпретатором `/usr/bin/python3` и режимом0755. Он принимает только фиксированные операции/модель; для фонового запуска write-тестов есть `--no-prompt`, после него агент обязан отдельно спросить пользователя о цвете/вентиляторах и активности встроенной клавиатуры. `keyboard-observe` остаётся интерактивным, т.к. нужен один физический Fn+F7. В sudoers разрешать только конкретные команды этого неизменяемого helper (сначала snapshot и bios, затем согласованные keyboard/fans/battery), а не python/sh/insmod или пользовательский изменяемый скрипт. Сборку/перезагрузку модуля на этом этапе оставить пользователю. Не нужен NOPASSWD:ALL или общий доступ к debugfs.
