# Архитектура и решения

`main.c` регистрирует platform device, WMI events, hwmon, battery hook, lightbar, экспериментальную keyboard LED и debugfs. Необязательный submodule может отказать, сохранив работу остальных; смотреть журнал, одного успеха insmod недостаточно.

## EC и питание

WMI method 4 получает 8-байтовый пакет. Все обращения, включая чтения, сериализованы одним mutex: это общий mailbox. `ec_update_bits` держит тот же mutex на всём read/modify/write. Он защищает только от других обращений этого драйвера, не от BIOS или сторонних драйверов. Некорректные ответы и firmware sentinel 0xfefefefe возвращают ошибку.

Для LAPAC71G функции батареи/Fn/fan-extras допускаются с BIOS семейства ACADL357 ревизии 0060; для исходных QC71 сохранён порог 0114. OEM string 18 должен быть непустым и состоять из пробелов. Номера ревизий разных семейств BIOS нельзя сравнивать по общему порогу 60.

BAT0 `charge_control_end_threshold`: 1..100; 100 кодируется 0. Статусный bit7 сохраняется атомарным RMW. EC значения 101..127 — ошибка данных. Немедленный readback после записи не встроен: задержка firmware пока неизвестна; аппаратный тест читает через 3 с. Запись90→80 и естественная зарядка78→80 с переходом Charging→Not charging на пороге80 подтверждены. CPU/GPU power limits не добавлялись: пользователь уточнил, что нужен лимит заряда.

## Вентиляторы

Телеметрия и PWM — два hwmon устройства (`qc71_laptop.hwmon.fan` и `.pwm`). PWM публикуется при capability fan_boost либо явно с `fan_control=1` на точном DMI LAPAC71G. Override экспериментален, сам по себе EC не меняет. Общий `pwm1_enable` управляет обоими вентиляторами; `pwm2_enable` не создаётся.

| Интерфейс | Смысл |
|---|---|
| pwm1_enable=0 | Оба вентилятора, PWM raw 200 (полная скорость), требует manual_control=1 |
| pwm1_enable=1 | Ручные pwm1/pwm2, 0..255, требует manual_control=1 |
| pwm1_enable=2 | Снять direct boost; кривая firmware, AppIsRunning не меняется |
| manual_control=0 | Сначала снять boost, затем AppIsRunning; полный явный возврат BIOS |

Не включать manual_control ради подсветки: он влияет на политику питания/горячие клавиши. Ручное управление требует отдельной команды. Fan mutex охватывает режим, PWM и полный handoff. При ошибке записи PWM после захвата прямого управления выполняется попытка возврата firmware с журналированием отказа. При suspend/unload снимается только прямое управление, запрошенное этим драйвером; при resume PWM автоматически не восстанавливается. Контроль/daemon после сна должен повторно выбрать режим явно.

Этот PM путь подтверждён одним коротким s2idle на AC: после ручных~90% и сна до helper cleanup уже были mode2/manual1/boost0, оба вентилятора замедлились. Последующий manual0 отдельно вернул полный BIOS. Сохранение manual1 при снятом boost ожидаемо: PM не сбрасывает глобальную политику приложения.

Длительный manual режим требует отдельного теста: TUXEDO legacy код перезапускает boost примерно раз в 50 мин из-за самопроизвольного повышения оборотов firmware. Здесь это без доказательств не перенесено. Watchdog для аварийно завершившегося userspace-контроллера не реализован; для обычной эксплуатации предпочтителен BIOS.

## Подсветка

Lightbar и keyboard LED — разные устройства. В lightbar исправлено чтение brightness: положительный байт управления не означает ошибку; соседние биты сохраняются атомарно.

Keyboard LED включается только параметром `keyboard_backlight=1`, точном DMI LAPAC71G и установленном бите возможностей 0x0766 bit2. Без бита возможностей LED не создаётся: сначала исследовать snapshot, не форсировать адреса. Нет записей EC при регистрации и удалении LED, нет переключения AppIsRunning. Требуются CONFIG_LEDS_CLASS_MULTICOLOR и CONFIG_POWER_SUPPLY; на этой плате проверяется доступность AC0/online. Read-only параметр `keyboard_backlight_protocol=intel-ac-dc-v1` отличает новый backend от первой экспериментальной сборки.

Стандартный LED `/sys/class/leds/qc71_laptop:rgb:kbd_backlight`: `multi_index` задаёт порядок, `multi_intensity` — RGB 0..255. `brightness=0` выключает свет; ненулевые значения округляются в четыре аппаратных уровня, при чтении это 64/128/191/255. Нулевой RGB реализован выключением, т.к. firmware может трактовать RGB 0,0,0 как цвет по умолчанию. Округление raw 0..50 ↔ 0..255 сохраняет все исходные значения.

Используется Intel AC/DC протокол: control07ea/07eb, RGB AC0769..6b и DC07ec..ee. Младшие три бита control — уровень0..4, bit3 — команда применения, bit4 — OFF, bit5 — rainbow. Запись уровня и восстановление включают bit3; firmware его очищает. Общий Uniwill brightness078c на P527 не управляет физической яркостью и больше не используется keyboard backend. Пользователь подтвердил AC красный level4/1/OFF/белыйrestorelevel2 и DC синий level4/1/OFF/красныйrestorelevel2. Автоматическое переключение белыйAC→красныйDC→белыйAC с сохранением обоих профилей также подтверждено. Rainbow ещё не проверен физически.

Getter возвращает настроенный уровень активного профиля, а не фактическую яркость после Fn или таймера активности. Native Fn+F7 меняет физический свет без изменения наблюдаемых настроек. Поэтому LED_BRIGHT_HW_CHANGED не объявляется; immediate1802 на P527 также не является достоверным getter. При первом тесте нужно разбудить встроенную клавиатуру обычной клавишей.

Power-supply notifier обновляет кэш активного AC/DC профиля только чтением. Setter при несовпадении источника питания с кэшем не пишет EC, запрашивает refresh и возвращает EAGAIN. Обычную запись после смены питания следует повторить, дождавшись обновления. LED core может выполнять callback асинхронно: успешный echo не доказывает применение; helper ждёт стабильного readback. Блокировки: refresh берёт led_access, дожидается LED work, затем keyboard_lock; callback берёт только keyboard_lock и EC mutex.

Изменение одной яркости сохраняет RGB и rainbow. Новый цвет отключает rainbow; отдельного API эффектов пока нет. Запись того же RGB неотличима от изменения одной яркости и сама не переключает rainbow в static. При ошибке после возможной записи восстанавливается исходный AC/DC банк с командой применения, кэш инвалидируется. Это восстанавливает настройки, но не скрытый native Fn-уровень. Чужие верхние биты control сохраняются атомарным RMW. Никогда не переносить исходные AC-цвета в DC при восстановлении helper после отключения адаптера.

Семантика PWM соответствует [Linux hwmon ABI](https://github.com/torvalds/linux/blob/master/Documentation/ABI/testing/sysfs-class-hwmon). Текущий протокол сравнивался с `../tuxedo-drivers/src/uniwill_leds.h` и `uniwill_keyboard.h`.
